Houme 이미지 생성 리팩토링

AI 이미지 생성 요청의 대용량 입력을 최적화해, 모놀리식 서버의 메모리 압박과 GC로 인한 일반 API 지연 위험을 낮춘 문제 해결

상황과 문제

Dev 환경에서 AI 이미지 생성 기능을 QA하던 중 JVM 힙 사용률이 3분 이상 80%를 넘는 경고가 반복 발생했습니다.

이미지 생성과 일반 조회 API를 하나의 JVM에서 처리하는 모놀리식 구조였기 때문에, 이미지 처리 부하가 GC pause를 거쳐 일반 API의 tail latency까지 악화시킬 위험이 있었습니다.

참고 이미지 원본 byte[], Base64 문자열 및 Gemini 요청 버퍼가 동시에 생성되며, 대형 객체가 G1의 Humongous 영역을 점유해 GC 회수 효율을 낮출 가능성이 있었습니다.

1. 운영과 동급인 perf 환경에서 메모리 회복과 API 간섭을 검증

검증 환경

  • t3.small급(2 vCPU / 약 2GiB) EC2에 Java 21, G1 GC, -Xms512m -Xmx512m으로 구성
  • develop 기준 HOUME-SERVER Docker 이미지와 PostgreSQL, Redis를 분리된 perf 환경에 배치하고, Prometheus와 Grafana로 GC, 힙 및 API 지표를 관측

관측

  • Gemini V4 이미지 생성 동시 5건을 3회 반복한 결과, 마지막 idle 구간에서 Old Gen, Heap after GC 및 Live Data가 함께 하락해 메모리 누수가 아님을 확인
  • 이미지 생성 5건과 GET /api/v1/landings를 함께 호출했을 때 조회 API p95가 19.63ms → 34.90ms로 상승
  • 같은 구간의 G1 Evacuation Pause가 약 15ms로 유사해, GC pause가 일반 API의 tail latency에 영향을 줄 수 있음을 검증

2. GC 옵션 대신 입력 데이터 자체를 줄이는 A/B 실험 설계

가설과 해결

  • GC 옵션만 조정하면 이미 할당된 대형 객체의 수집 시점만 바뀌므로, GC 대상인 원본 이미지와 Base64 문자열 자체를 줄이는 방식을 우선 검증
  • 이용량이 적은 새벽 4시에 스케줄러가 대상 이미지를 순회(sweep)해 WebP 파생 이미지를 미리 생성해 저장하고, 이미지 생성 요청에서는 저장된 최적화 이미지를 재사용하도록 입력 경로를 개선
  • 동일한 Gemini V4 요청을 동시 5건씩 3회 실행해 기존 원본 전달 모드와 최적화 전달 모드를 비교

3. 운영 안정성을 우선한 선택: Adaptive G1 유지

의사결정

  • 입력 최적화 이후 IHOP 30% 및 40%와 기본 Adaptive G1을 비교했으나, 고정 IHOP는 메모리 여유와 누적 pause 사이의 트레이드오프가 있었습니다.
  • 특정 GC 옵션을 일괄 적용하는 대신, 입력 최적화를 우선 배포하고 기본 Adaptive G1을 유지하는 것이 운영 위험이 낮다고 판단했습니다.

운영 계획

  • 반복 부하, 일반 API 간섭, 이미지 입력 A/B, IHOP 비교를 위한 k6 시나리오와 실행 오버라이드, 중단 및 해석 기준 문서를 스프린트마다 동일 조건으로 재검증할 수 있는 perf 운영 자산으로 정리
  • Grafana에서 Old Gen과 Heap after GC, Live Data, GC pause, 일반 API p95/p99 및 Swap in/out을 지속 관측
  • Old Gen이 70~80% 이상에서 지속 상승하거나 Full GC, evacuation failure 또는 tail latency 악화가 반복될 때 G1 옵션 A/B 테스트를 재개

Clustar Agent Harness

Clustar 2차 스프린트, AI 에이전트 API 작업의 컨텍스트 선별과 로그 기반 개선

API 변경 요청을 저장소 구조와 검증 기준에 연결하는 Agent Harness를 구축해, AI 에이전트의 불필요한 탐색과 토큰 사용을 줄인 문제 해결

문제

API 수정 요청마다 에이전트가 관련 없는 모듈까지 넓게 탐색하고, 이미 확인한 규칙과 파일을 반복해서 읽으면서 컨텍스트 입력과 구현 시작 시간이 늘어났습니다.

최근 API 변경 이슈 5건의 명령 실행, 파일 탐색 및 토큰 로그를 분석한 결과, 구현 능력보다 자연어 요청을 실제 도메인, 소스 파일, 테스트 및 검증 명령으로 연결하는 탐색 과정에서 더 큰 비용이 발생했습니다.

1. 정적 규칙과 작업별 컨텍스트를 분리하는 Harness 설계

대안 비교와 결정

  • 상위 모델 사용은 비용을 높이고, 프롬프트 템플릿 강화는 개발자가 매번 관련 정보를 직접 작성해야 했습니다.
  • AGENTS.md는 공통 아키텍처 계약으로 유지하되, 요청별 파일 범위까지 담으면 규칙 자체가 비대해지는 한계가 있었습니다.
  • 따라서 공통 규칙은 유지하고, 각 API 변경 요청에 필요한 컨텍스트만 동적으로 선별하는 Agent Harness를 구축했습니다.

처리 흐름

단계처리
1. 요청 분류Skill이 자연어 요청의 도메인과 변경 유형을 분류
2. 컨텍스트 생성전처리 스크립트가 규칙, 우선 파일, API 계약, 테스트를 수집해 JSON 생성
3. 구현과 검증에이전트가 선별된 시작점부터 구현하고 관련 테스트 후 전체 빌드로 검증
4. 작업 기록Codex CLI JSONL 이벤트와 Git, Gradle 결과를 수집해 작업 요약 JSON 생성

요청 분류와 컨텍스트 생성 방식

1. 요청 분류Skill이 자연어 요청에서 도메인, 변경 유형, 검색 키워드를 추출
2. 파일 우선순위 계산파일명, 코드 내용, 도메인 패키지, 계층, 테스트 여부에 가중치 적용
3. 컨텍스트 JSON 생성규칙, 우선 파일, API 계약, 테스트, 검증 명령을 에이전트에 제공
request = classify(text)
# { domain, changeType, searchTerms }

candidates = rankFiles(repository, request.searchTerms,
  weights=[fileName, content, domain, layer, test])

context = {
  rules: findApplicableAgents(candidates),
  priorityFiles: topRanked(candidates),
  endpoints: extractApiContracts(candidates),
  validation: selectValidationCommands(request.domain)
}

실험 통제

  • 동일한 모델, 요청 내용, 기준 커밋, 최종 검증 명령을 유지하고 기존 정답을 참조하지 못하도록 Git 이력과 원격 저장소 접근을 제한했습니다.

3. 에이전트 행동 로그를 Harness 개선의 피드백 루프로 활용

관측 가능한 작업 로그

  • codex exec --json으로 명령 실행, 파일 탐색 순서, 토큰 사용량, 테스트 종료 코드와 작업 시간을 JSONL로 수집했습니다.
  • 작업 종료 후 변경 파일과 전체 빌드 결과를 별도 JSON으로 요약하고, 원시 프롬프트와 민감정보가 포함될 수 있는 JSONL은 Git에서 제외했습니다.

피드백 루프와 해석

  • 후보 파일과 실제 변경 파일을 비교해 누락과 오탐을 분석하고, 파일 점수와 요청 분류 규칙을 다음 작업에 반영했습니다.
  • 출력 토큰은 0.6%만 감소한 반면 입력과 전체 토큰은 크게 줄어, 구현 결과를 축소한 것이 아니라 구현 전 불필요한 탐색과 컨텍스트 수집을 줄인 효과임을 확인했습니다.
  • 후보 파일은 절대적인 허용 목록이 아닌 우선순위가 높은 시작점으로 정의해, import 관계와 실패한 테스트, 미충족 요구사항이 있을 때만 탐색 범위를 확장했습니다.

  • 이미 배포 가능한 이미지가 있는데도 다음 빌드용 캐시 완료까지 현재 배포가 대기하는 구조 확인

해결

  • cache export는 다음 빌드의 성공 조건, image push는 현재 배포의 성공 조건으로 책임을 분리
  • 현재 배포의 완료 기준을 Job 종료 → image push 완료로 변경
  • 기존 로그 tailer에서 push 완료 마커를 감지해 즉시 배포 시작
  • 감지 실패·빌드 실패 시 기존 Job 종료 대기로 자동 fallback

  • 잔여 리스크는 AWS 백서로 관리 네트워크의 물리 계층 전송 보호·VPC 테넌트 격리를 검토해 평가 후 수용
  • 별도로 공격면 축소 - Managed Prefix List + Custom Header 검증으로 본인 CloudFront를 거친 요청만 ALB에서 허용

  • 502 장애 해결 및 서비스 정상화
  • AWS CloudShell에서 동일 ALB 기준 n=100 측정 → 15.7ms → 5.1ms, 구간 신규 연결 지연 67% 개선
